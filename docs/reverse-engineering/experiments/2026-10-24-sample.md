# 2026-10-24 — SAMPLE: which rows Desktop picks (issues #211, #212)

## Why

`SAMPLE(n, table, orderBy [, order [, orderBy [, order]]...])` returns n rows
spread over the table in the order of its orderBy expressions. Pull request
#208 (@allanon2) reported that pbix-mcp picked other rows than Desktop,
described four differences, and noted that Desktop's line-chart queries use
SAMPLE (not checked here). Outside pull requests are not merged on trust: the
PR's text and diff were read as a description of the problem only, none of
its code was used, and every answer below comes from our own queries to our
own Desktop. The implementation in `src/pbix_mcp/dax/engine.py`
(`_fn_sample`, `_sample_order`, `_evenly_spaced`, and `_order_pairs` and
`_row_count_arg`, which TOPN uses too) was written from these answers.

## Method

- Power BI Desktop 2.152, its local Analysis Services instance queried over
  ADOMD, Norwegian locale (error texts below are our translations).
- 173 probes, each one `EVALUATE ROW("v", <expression>)` over tables built
  with `GENERATESERIES` and `DATATABLE` only, so no model's data is involved.
  A probe prints the picked rows as one value: `CONCATENATEX(SAMPLE(...),
  [v], ",", [v], ASC)`, or `COUNTROWS(...) & ":" & CONCATENATEX(...)` where an
  empty table and BLANK must read apart.
- Every probe was run twice; all 173 answers were the same both times,
  including the ones that depend on how Desktop orders tied rows.
- The probes: the PR's 53 cases re-measured (ids `pr-*`), and 120 of our own
  (ids `x-*`): n as a fraction, negative, BLANK, text, TRUE / FALSE and very
  large; every order word and some that are not order words; one to three
  orderBy expressions with mixed orders and the arguments in odd positions;
  tables of 0 to 3 rows; n = N - 1; sizes where float and exact arithmetic
  disagree; text keys in the collation; BLANK among texts, among numbers and
  next to 0; dates; expression keys; duplicate rows; rows tied under every
  orderBy; four TOPN side probes.
- The probes and Desktop's answers are the expected values of
  `tests/test_issue211_sample.py` (166 probes) and
  `tests/test_issue212_topn_n.py` (4 TOPN probes), with the ids used here.
  The other three: `x-expr-countrows-asc` (an orderBy that reads the outer
  row's `[v]` inside an inner FILTER, Desktop 1,6,10,15,20) and
  `x-rowctx-sumx-bare` (the same pattern in SUMX, Desktop 190) show a
  separate engine defect, not SAMPLE's; `x-tie-unordered-v-n5` (SAMPLE's
  output order without an order of CONCATENATEX's own) was 1,6,11,15,20.

## What Desktop does

### Which positions

The picked rows are positions `floor(i * step + 1/2)`, i = 0 .. n - 1, of the
ordered table, with `step = (N - 1) / (n - 1)` computed first as a double.
Of the 55 answers that show positions (2 <= n < N):

| rule | fits | fails on |
|---|---|---|
| step as a double first, then `floor(i * step + 0.5)` | 55 | -- |
| exact fractions, a half rounding up | 50 | 99 of 100, 29 of 35, 23 of 50, 45 of 50, 59 of 60 |
| a running sum `p += step` | 49 | 13 of 14, 15 of 16, 23 of 24, 29 of 35, 59 of 60, 911 of 912 |
| exact fractions, a half to even (0.9.145's `round()`) | 44 | 3, 5 and 7 of 10, 5 of 11, 7 of 100, 7 of 1000, ... |

So 3 of 10 are rows 1, 6, 10 (0.9.145: 1, 5, 10), and 99 of 100 leave out
row 51 where exact arithmetic leaves out 50. Spacing is by position, not by
value: the squares 1 .. 900, n = 4, give 1, 121, 400, 900. n = 1 is the first
row in the order, n >= N every row (3502 of 912 is 912 rows).

### n

- Rounded half up: 0.4 is no rows, 0.5 and 0.6 one, 1.5 two, 2.4 two, 2.5
  and 2.6 three, 9.5 and 10.5 all ten. `COUNTROWS(T) / 4` = 2.5 is three.
- BLANK and FALSE are no rows, TRUE one, `"3"` three, 3,000,000,000 the
  whole table.
- 0 is no rows (COUNTROWS is BLANK). A negative n is an error, -0.5 too:
  "The SAMPLE function can only be used with a non-negative sample size
  argument."

### The order arguments

- Paired by position: the argument after an orderBy is its order. ASC, 1,
  TRUE and TRUE() ascend; DESC, 0, FALSE and FALSE() descend; case and
  spacing do not matter (`asc`, `TRUE ( )`). With no order the last orderBy
  descends.
- Anything else in an order's place is refused before the query runs: 2, -1,
  `1 + 0`, BLANK(), `"ASC"`, `[v]` -- "Unexpected value for the ORDER argument
  in the function SAMPLE. Use 0/FALSE/DESC for descending order or
  1/TRUE/ASC for ascending order." So `SAMPLE(5, T, [a], [v])` and
  `SAMPLE(5, T, [a], [v], ASC)` are errors, while `SAMPLE(5, T, [v], 1, [a])`
  orders by [v] ascending and then [a] descending.
- At least one orderBy: `SAMPLE(3, T)` is refused, "Too few arguments were
  passed to the SAMPLE function. The minimum argument count for the function
  is 3."
- Every orderBy counts, each with its own order. Over four rows per [a] (v =
  1 .. 20): `[a], ASC, [v], DESC` picks 4, 7, 10, 14, 17; `[a], DESC, [v],
  ASC` 4, 7, 11, 14, 17; `[a], ASC, [v]` 4, 7, 10, 14, 17; three keys `[a],
  ASC, [b], DESC, [v], ASC` 1, 7, 10, 14, 20.

### The order of values

- Numbers, dates and expressions by value (`[v] * -1`, `-[v]`,
  `MOD([v] * 7, 20)`); text in the model's collation (Apple, apricot, banana,
  ..., pear; "1", "10", "2", ...; `_x` < `1x` < `a10` < `a2` < `Americas`).
- BLANK among numbers orders as 0: over -4 .. 4 with BLANK for 0, 3 picked
  ascending or descending are -4, the BLANK and 4, and 2 picked are -4 and 4
  (BLANK first, as 0.9.145 ordered it, gives other rows). Over 2, BLANK, 0,
  -1, 1 the BLANK is second ascending and fourth descending (3 picked
  ascending are -1, the 0 and 2; 4 descending are 2, 1, the BLANK and -1):
  the BLANK sorts just before the 0. That pair is the only evidence for
  "just before"; with BLANK and 0 tied, Desktop's own tie order could give the
  same two answers (see below).
- BLANK among texts sorts first: over c, BLANK, a, b, 3 picked ascending are
  the BLANK, b and c, descending c, a and the BLANK.
- Duplicate rows are kept: 3 of a table with every value twice is 3 rows,
  values 0, 2, 4.

### TOPN (issue #212)

- n rounds half up: `TOPN(2.5, ...)` and `TOPN(2.6, ...)` are 3 rows (0.9.145:
  2).
- The same pairing by position: `TOPN(3, T, [a], [v])` and `TOPN(3, T, [v],
  2)` are refused with the same message naming TOPN. 0.9.145 read [v] and 2
  as further orderBys.

## Compared with PR #208's report

- **Agreed.** All 53 of the PR's answers came out the same on our Desktop
  2.152 (the PR measured 2.157): spacing by position with halves rounding up,
  1 ascending and 0 descending, DESC by default, every orderBy counting, n = 0
  no rows, n = 1 the first row, n >= N every row. The PR's tie answer for
  `[a], ASC` alone (v = 2, 6, 10, 15, 20) is ours too (`x-tie-a-n5-asc`).
- **Confirmed where the PR had not measured.** TRUE and FALSE read as 1 and 0.
- **Not as the PR expected.** A negative n is an error, not "no rows
  likewise". The PR computes the positions in exact integer arithmetic; that
  fits its own cases, but Desktop computes the step as a double first, and
  the exact rule misses 5 of our 55 position answers.
- **Not covered by the PR.** Fractional, BLANK, text and boolean n; the order
  words beyond ASC / DESC / 1 / 0, and the errors for anything else (the PR
  reads a non-word as the next orderBy, as TOPN did); SAMPLE without an
  orderBy; BLANK keys; TOPN's n.

## Open: rows tied under every orderBy

Desktop's choice among fully tied rows is deterministic -- the same answers in
both runs -- but it is not the table's order and not its reverse:

- For `[a], ASC` alone over groups of four, the nine tie probes (n = 2, 3, 4,
  5, 6, 10, 15, 19 and the unordered output of 19) all fit one internal order:
  2, 3, 1, 4 | 5, 6, 7, 8 | 11, 9, 10, 12 | 13 .. 16 | 17 .. 20 -- the table's
  order with two groups shuffled, as an unstable sort leaves rows.
- The same rows built in reverse (`x-tie-arev-n5-asc`: 1, 5, 11, 15, 19), the
  same rows descending (`x-tie-a-n5-desc`: 2, 6, 10, 16, 20; not the reverse
  of the ascending order) and ten rows all tied (2 of them: rows 6 and 10;
  3, 5 and 9 of them: the table's order) shuffle differently.

No rule stated from these answers reproduces them, so pbix-mcp keeps tied
rows in the table's order (stable sorts, as its TOPN) and the tests compare
only what the orderBy decides: the number of rows and their orderBy values.
A probe that would settle the BLANK-next-to-0 question above: the same five
values with the 0 placed before the BLANK in the table.
